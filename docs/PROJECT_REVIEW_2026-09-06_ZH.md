# LeRobot 数据清洗与 LingBot-VLA 对接：项目复盘与后续计划

整理日期：2026-09-06。范围：本次对话中提出的目标、实施修改、本地验证和用户提供的服务器运行记录。

**截至目前：完整数据的分批数值/结构审计已通过，所引用视频的完整解码审计也已通过；已提供正式清洗命令，但尚未收到完整数据清洗输出成功的报告。LingBot 归一化、实际加载和训练尚未确认完成。**

## 一、我们要完成什么

最初的目标是理解并修改一个 GitHub 上的 LeRobot 清洗项目，让它能够为 LingBot-VLA 提供可用的训练数据，并将自己的改进项目整理成别人能理解、能复用的代码库。

这个目标包含三个层面：

1. **数据处理**：确认数据格式、内容与完整性，按明确的规则生成可追溯的新数据集。
2. **训练对接**：将数据中的状态、动作和相机字段映射到 LingBot 的输入，配置归一化与训练入口，并实际验证加载和训练。
3. **工程交付**：把代码、配置、测试、文档和运行方法整理好，使环境可重建、过程可记录、结果可复查。

清洗成功不是训练成功，文件能读也不代表每段演示都适合模仿学习。我们逐步将这些层面分开验证。

## 二、整体思路是怎样形成的

整个过程可以概括为：

**理解原项目 → 读取真实样例 → 修正机器人/格式假设 → 小样例实现与测试 → 适配服务器完整规模 → 定位额外分片 → 完整审计 → 正式清洗 → LingBot 加载、归一化与训练验证。**

### 2. 用本地真实数据纠正最初假设

读取“数据实例”后确认：数据已经是 LeRobot v3.0，机器人是 DROID 数据中的 Franka 单臂。
因此当前数据不需要 v2.1→v3.0 转换，也不能套用 R1Pro 的 16 维双臂映射。

本地样例的实际信息：

| 项目 | 结果 |
| --- | --- |
| 演示数 | 100 |
| 帧数 | 32,212 |
| 任务数 | 47 |
| 帧率 | 15 Hz |
| 状态、动作 | 各 8 维：7 个关节位置与 1 个夹爪位置 |
| 相机 | 两路外部相机、一路腕部相机 |
| 失败标签 | 19 段演示 |
| 非有限值 | 扫描字段未发现 NaN/Inf |

逐行核对了合并向量与拆分字段的一致性，例如 `action[:7]` 对应 `action.joint_position`，最后一维对应夹爪位置。动作位置与动作速度字段并不相同。

由此作出的具体选择：

- 使用 7+1 的实际映射，三个相机名称忠实对应其视角。
- 保留连续夹爪值，不自动二值化。
- 映射中 `subtract_state: false`，当前保留位置动作；未擅自改成相对状态的增量。
- 对重复存储的位置字段声明别名关系，修改时同步，避免两份表示互相矛盾。
- 保留 R1Pro 模板并注明未验证，不让它成为 DROID 的默认配置。

**格式与映射的区别：**v3.0 解决数据怎样组织和存储；映射解决每个字段、每一维的意义以及模型如何读取。已经是 v3.0 仍然需要正确映射，但不意味着需要再转换一遍文件格式。

### 3. 先实现适合样例的保守清洗

原项目面向 GR00T v2.1，依赖 `modality.json` 和原有逐集文件组织方式。
这份 v3 数据使用共享 parquet 和共享视频，通过逐集偏移关联，不能直接交给原 v2.1 流程。

我们新增原生 v3 检查、清洗入口，保持每帧顺序、额外字段、任务信息和视频偏移，重算数值统计，复制视频并校验 SHA256。
同时修复测试文件末尾误贴的执行代码、旧格式转换时报告丢失的问题，以及 README 安装命令缺失引号等问题。

本地样例已实际生成清洗副本，并比较了全部数据列及非统计类逐集元数据。
结果是数值改动 0、删帧 0；说明数据通过了当前检查，不代表所有演示的动作质量都完美。

### 4. 从小样例扩大到完整数据集

服务器提供的数据并非本地的 100 集样例，而是 95,658 集、27,630,375 帧。
旧实现设置 100 万帧上限，触发保护后，我们没有直接解除限制，而是先检查实际资源。

你使用 A800 80GB，但这段清洗代码使用 CPU 和系统内存，不会自动借用显存。
`free -h` 显示宿主机约 1 TiB 内存、915 GiB 可用；进一步读取 cgroup v1 后发现容器实际限额为 96 GiB，当前占用约 2.15 GiB。
数据表约 12 GB、元数据 566 MB、视频约 373 GB，文件系统当时剩余约 3.6 TB。

压缩文件大小不能直接当作 Pandas 内存占用，全量拼接及中间副本可能超出容器额度。因此批准修改后增加分批引擎：

- 默认每批读取 8,192 行，不拼接完整数据集。
- 逐集元数据每批读取/写出 64 条，不在内存里保留全部逐集统计。
- 保留完整单集进行必要的插值与统计，默认单集上限 100,000 帧；支持演示跨读取批次和数据文件。
- 全局 mean/std/min/max/count 累计全部帧；全局分位数用固定容量均匀抽样，默认 32,768 行/字段，随机种子 0；逐集分位数按该集完整数据计算。
- 增加进度条、磁盘预检、输出复核和阶段级续跑。

`max_frames: 30000000` 现在是分批引擎的总数据规模保护，不是一次读入 3,000 万帧。
实际内存还受字符串长度、解压缓冲等影响，批次数量不等于进程 RAM 峰值。

### 5. 定位“实际行数多于声明帧数”

新引擎随后报错：数据文件总行数与 `total_frames` 不一致。这次通过逐步增加证据来定位：

| 排查步骤 | 结果 | 排除或确认了什么 |
| --- | --- | --- |
| 比较常规扫描与递归扫描 | 均找到 156 个 parquet，全部可读 | 不是漏扫目录或文件头读取失败 |
| 汇总数据文件行数 | 39,995,463 行 | 比元数据多 12,365,088 行 |
| 汇总逐集元数据 | 95,658 条，length 总和 27,630,375，区间连续 | info 与逐集元数据一致 |
| 分批检查 index、episode_index | 均未越界，文件内连续，仅 file-086 处发生一次回退 | 存在重复索引区间 |
| 检查元数据文件引用 | 只引用 file-000～file-085 | 后 70 个文件未被当前元数据引用 |

覆盖关系最终明确为：

- 前 86 个文件：索引 0～27,630,374，正好覆盖声明数据。
- 后 70 个文件：索引 15,253,563～27,618,650，额外包含 12,365,088 行。

不能由索引重复推断动作内容逐字相同，也不能确定这些额外文件为何产生。
因此没有删除原始分片、没有修改声明帧数，而是新增显式 `metadata_referenced` 策略：按逐集元数据引用选择文件，要求所选数据完整覆盖声明帧数，再继续检查每帧和视频关联。

默认 strict 策略保留。当前服务器应使用 `droid_v3_referenced.yaml`，生成的输出最终仍用 strict 复核，并记录选中和排除文件清单。

## 三、运行环境与长任务遇到了哪些问题

| 问题 | 判断与解决方法 |
| --- | --- |
| `python: command not found` | 检查发现系统有 python3；后续激活虚拟环境后使用 python。不能仅凭终端目录判断环境已激活。 |
| `No module named pip` | 系统 Python 缺 pip；补齐发行版组件并创建清洗虚拟环境。 |
| 缺少 ensurepip，venv 创建失败 | Debian/Ubuntu 容器补装 `python3.10-venv`，然后创建环境；已有可用环境则优先复用。 |
| 换任务后原环境部分失效 | 任务标识发生变化，旧环境目录虽保留，系统 Python 组件未必相同；检查而不是认定整个环境已丢失。 |
| `No module named distutils.cmd` | 补齐系统 distutils 等组件，恢复旧环境中的 pip。 |
| 项目名称 UNKNOWN、缺少 bdist_wheel | 当前构建工具不足/过旧；安装可用的 setuptools 与 wheel，再绑定新项目。 |
| 更新目录后环境仍指向旧代码 | 激活可用环境，在新项目根目录做 editable 安装；依赖齐全时用 `--no-deps --no-build-isolation`，并核对导入路径。 |
| 安装视频 extra 下载超时 | 失败发生在隔离构建依赖下载；已有清洗器可直接安装 `av>=14` 二进制包，延长超时，避免重复构建项目。 |
| 每次上传 2.0/3.0 就重建环境 | 并无必要；代码与环境可分开，环境复用的前提是依赖和系统组件确实可用。跨容器持久化需看平台能力。 |
| GPU 预订时长不足 | 当前解码使用 CPU；更换卡不等于进程继续。保留镜像、数据卷、代码与环境清单，并区分容器存活和终端连接。 |
| tmux 中找不到运行结果 | 滚动缓冲不便查看时，优先查 `tee` 保存的日志；命令历史只保存命令，不能证明结果。 |

前期让你随每个新目录建立环境的建议造成了重复操作；后来明确改为优先复用已有可用环境。
同样，`--no-build-isolation` 不是无条件可用，它依赖环境里已有兼容的构建工具。

关于任务保留，我们明确了两个边界：

- tmux/tee：tmux 可应对终端断连，tee 保存输出；它们不能让被释放容器里的进程继续运行。
- 程序检查点：正式清洗支持阶段级恢复；当前只读视频审计未实现持久检查点，不能使用 `--resume` 接着解码。

正式清洗中，未完成的数值阶段会重跑；已完成数值阶段可经哈希验证后复用；已复制视频可经校验后跳过。
输入、配置或路径改变时拒绝复用检查点。备份必须放到确认持久的存储，`/tmp` 打包文件需及时下载；不能只根据 `/data` 这个目录名推断平台会保留它。

## 六、当前策略做什么，不做什么

当前配置：`engine: streaming`、`data_file_policy: metadata_referenced`、`nonfinite: error`、`bounds: {}`。

实际策略是保留所有选定数据的演示和帧，排除未引用的数据分片，检查一致性、重新统计、复制验证视频。
没有启用动作限幅、平滑、删失败演示、删静止帧、相机裁剪或夹爪二值化。

两种“没有改动”不能混淆：

- `changed_values: {}`：未修改数值。对于已经通过有限性检查、未启用限幅的数据，这很合理。
- `rows_removed: 0`：在选中的有效数据内部未删帧；原始目录中额外的 70 个未引用文件仍被排除在输出之外。

全局近似分位数会在报告中标注；`meta/stats.json` 属于数据集统计，不能直接代替 LingBot 映射后的归一化文件。
当前位置动作保留为绝对值；若决定切换相对动作，需要同步检查控制含义、部署还原，并重新计算归一化统计。

## 七、下一步具体怎么做

### 优先级 1：保存成功审计证据并生成完整基线

保留包含 full_decode 的日志，记录数据路径、配置版本及运行命令。
当前容器中先确认实际激活的环境和项目路径正确，无需因代码更新再次创建环境。

在服务器项目根目录、已激活环境中执行正式清洗：

```bash
cd /code/lerobot_cleaner-match_lingbotVLA_3.0

DATASET="/data/bai0111/droid_1_0_1_lerobotv3"
CONFIG="/code/lerobot_cleaner-match_lingbotVLA_3.0/configs/cleaning/droid_v3_referenced.yaml"
OUTPUT="/data/bai0111/droid_1_0_1_clean_v3_referenced"

set -o pipefail
python -m scripts.run_droid_clean \
  --dataset "$DATASET" \
  --config "$CONFIG" \
  --output "$OUTPUT" \
  2>&1 | tee "droid_clean_$(date +%Y%m%d_%H%M%S).log"
```

这是此前给出的下一步，尚未收到成功结束的记录。如果你实际上已经完成，优先检查报告，不要重复运行。
已有完整输出不会覆盖；若存在 `.partial`，需核对是同一个输入和配置的未完成任务，再决定使用 `--resume`。

这次无需再加 `--verify-videos`：已完成的源视频完整审计日志，加上本次复制 SHA256 校验，可以分别记录源视频检查和副本一致性。
这并不是程序自动读取旧日志、自动继承 full_decode 状态；本次报告仍可能写 metadata_only，应将两份证据一起保存。

正式清洗耗时包括重新计算统计、复制约数百 GB 视频、哈希验证和输出审计，不能按只读审计时间推算。

### 优先级 2：检查输出，而不是只看进度条 100%

```bash
cat "$OUTPUT/cleaning_report/report.md"
```

同时检查 `report.json` 与 `data_file_selection.json`：

- 演示和帧数是否仍为 95,658、27,630,375。
- 文件是否按预期选中 86 个、排除 70 个。
- 数值改动和删帧是否符合配置，默认预期均为 0。
- 是否完成视频复制校验和输出严格复核。
- 是否记录统计方法、使用配置、日志与输出路径。

### 优先级 3：接入 LingBot，先验证少量数据

确认 LingBot 的实际源码、依赖、权重、数据路径和映射路径；清洗虚拟环境不等于训练环境。
先尝试读取一个样本或一批数据，核对三个视角、7+1 维有效状态/动作、填充维度、任务文本和短演示的动作块处理。

确定训练与验证划分，以完整演示为单位，避免同段演示的相邻帧分到两侧；疑似近重复采集也应考虑放在同一侧。
按最终训练数据和动作映射计算 LingBot 专用归一化统计，避免把验证集统计泄漏进训练预处理。
先运行少量训练步骤，确认损失有限、前向/反向和保存加载正常，再决定长时间训练参数。

这部分不能承诺“一张 A800 一定按现有 YAML 跑通”，训练并行方式、显存占用、模型权重和库版本仍需实测。

## 九、这段工作最重要的经验

1. **先看实际数据再写配置。** 最初的 R1Pro 假设在读取 DROID 样例后及时修正。
2. **先确定真实资源上限再扩大规模。** 显存、宿主机 RAM、容器内存限额是不同资源。
3. **报错先核对事实，不通过改声明绕过去。** 行数不一致最终定位到未引用分片，而不是简单修改 total_frames。
4. **把处理策略写成可复查的配置。** 严格默认、显式选片、输出排除清单，使处理决定可以复现。
5. **每个成功结论都有边界。** 静态映射通过、视频解码通过、清洗成功、训练成功分别对应不同证据。
6. **长任务必须有日志，真正续跑还需要程序检查点。** tmux 不能替代持久化数据和检查点。
7. **清洗质量应通过后续评估判断。** 删除更多帧或改变更多数值，不自动意味着训练数据更好。

当前最直接的工作是完成并核验完整清洗基线，随后验证 LingBot 实际加载、归一化和小规模训练。更激进的数据筛选应作为单独实验版本，与基线比较。
